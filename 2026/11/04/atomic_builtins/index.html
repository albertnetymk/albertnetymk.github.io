Atomic Builtins and Compiler Barriers

Nov 4 2026

GCC and Clang provide __atomic_* builtins for atomic access to shared data in C and C++ programs. Each operation’s memory-order argument sets the ordering constraints on surrounding accesses. The call-like syntax may suggest an opaque function, but the compiler knows each builtin’s semantics and may move code when that order allows it, so these builtins are not general compiler barriers.

§What the asm shows

With release or a compiler barrier, each update to sum stays before the corresponding store to flag. With relaxed ordering, clang moves the update out of the loop and writes sum once afterward.

On x64, a release store is a plain mov. The difference here is compiler ordering, not a hardware fence.

The pragma prevents unrolling, so each asm block shows one loop body. Without it, clang still moves the relaxed update out of the loop.

__atomic_store_n is the example here. Other __atomic operations also use their requested memory order to constrain compiler motion.
